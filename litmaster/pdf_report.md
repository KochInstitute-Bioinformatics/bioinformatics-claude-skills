# Stage 7: PDF report for a reader (optional)

Use when the user wants a document to hand to a person: a literature summary for a scientist, or a technical report about the method. A PDF is the last step; it adds no evidence. Everything in it must already be in `evidence_table.json` (literature report) or in a file you can name (technical report).

## A. Literature summary for a scientist

**Before you start:** stages 5 and 6 are done, `evidence_table.json` exists and the report passed `s5_check_report.py`. If a statement you want in the PDF has no quote in the table (for example "this study uses dataset X, which is also in your figure"), add the claim to `claims.json`, re-run stage 5, and only then write it.

1. **Write the narrative body** in HTML from `report_template/narrative_skeleton.html`: key points box, a direction-of-evidence table with grades, one section per gene or topic, "how this relates to the reader's data" (only if known), suggested checks, a "do not cite" box for retracted papers flagged at screening, the sources placeholder, and a methods and limits box. Refer to sources only by placeholder: `{{S:PMID,PMID}}` gives the numbers, `{{SOURCES}}` generates the sources section (authors, journal, DOI, read level, grade, exact quotes with their section).
2. **Writing rules (all learned from mistakes in the first reports):**
   - Lead with the findings. A reader should get the answer from the first page.
   - Write for the reader: "the current figure", "the project data", never "our" or "we" in a document for an outside reader (the build warns).
   - Every claim carries a source number and a grade (T1 to T4); text taken from a source is in curly quotes and must be part of an evidence quote (the build refuses otherwise).
   - Mark hypotheses and suggestions as such; never present them as findings of the papers.
   - Do **not** state facts about the reader's own data unless the user confirmed them; list them at hand-over for confirmation.
   - Audit every paraphrase against its quote once more: in the first report, two numbers (a cohort size and a count of papers read) went beyond what the quotes supported.
   - State the AI's role and limits in the methods box (who searched, read and graded; abstract-only sources; figures not opened; absence of retrieved papers is not proof of absence).
3. **Build** with a Python that has WeasyPrint (for example a conda env that has it):
   `python $S/s6_make_pdf.py $W narrative.html report.pdf --title "..." --subtitle "..." --footer "..." --date YYYY-MM-DD`
   The script resolves the placeholders, generates the sources section from the evidence table, **refuses to build** if narrative text in curly quotes is not in the table or a PMID is unknown, and warns about first-person words and sources never referred to. It writes the HTML next to the PDF.
4. **Look at every page.** Render page images with the ToolUniverse venv Python (it has `pypdfium2`; the build prints a note if its own Python does not) and view them. Check: text overflowing boxes or tables, a box split across pages, a heading stranded at the bottom of a page, raw markup or entities (`&lt;i&gt;`) in titles, black squares (never use Unicode super or subscripts with reportlab; WeasyPrint renders them), glued abstract section labels (exact as retrieved; the template explains them), blank or near-empty pages. Fix and rebuild.
5. **Hand over** with a short list: the statements that came from the user's own notes, the abstract-only sources, and anything the build warned about.

## B. Technical report about the method

For a technical audience (how the skill was built, how it compares with other approaches):
- **Every number comes from a file.** Recompute from the logs and result files while writing; do not recall numbers from the conversation. List the source file of each figure in an appendix. In the first technical report this caught a mislabeled table column, a false "only" claim and three wrong details.
- State the conditions of each comparison (who drove each run, what it had seen, what was tuned on what), separate measured from inferred, and mark "not run" and "not measured" as gaps, never as zero.
- Include a threats-to-validity section (development-set contamination, reference set built from the compared approaches, one grader, unequal conditions) and an evaluation design that fixes the protocol before running.
- Figures can be inline SVG generated by script (see `results/.../pdf_report/build_tech_pdf.py` for a worked example); build with WeasyPrint and review every page as in A.4.

## Worked example and tests
Worked example narrative: `report_template/narrative_skeleton.html` (fill it in, then build with `s6_make_pdf.py`). In development the stage was checked as follows: a good narrative builds; a fabricated quote, an unknown PMID and a missing sources placeholder are refused; first-person wording is warned. Those test scripts are not part of this folder.

## Environment notes
WeasyPrint is needed for the build; it was not in the ToolUniverse venv used in development, so use a separate Python for this stage. `pypdfium2` and `pdfplumber` (optional) render page previews and text checks. The build is light (no network) and does not need Slurm.

## Tested (2026-11-20)
On a development example, regenerating a hand-built 9-page summary through this stage gave 99.93% word-level similarity. Three deliberate errors: a fabricated quote and an unknown PMID were refused (no PDF built), first-person wording produced a warning.
